# Дизайн локальных сетей (Local Nets) - NC 2045

Этот документ служит для обсуждения и фиксации архитектурных решений по сборке локальных сетей из комнат.

## 1. Архитектурные вопросы к обсуждению

### 1.1. Привязка к физическому миру
*   **Вопрос:** Как должна происходить связь между физическим зданием/декой и цифровым гридом? 
*   **Предложение:** Использовать компонент `NetNodeComponent` на физическом объекте (например, сервере дома), который хранит `EntityUid` (или `NetEntity`) своего цифрового грида. При нажатии "TEST" система ищет ближайший узел или использует деку как точку входа.
**Ответ:** пока что остаемся на нынешнем варианте, потом уже мы сделаем как надо. Сейчас у нас будет условно один грид на карте и мы будем с этим работать

### 1.2. Пространственная изоляция
*   **Вопрос:** Если все локальные сети живут на одной "NetMap", как мы будем гарантировать, что они не пересекаются при расширении?
*   **Предложение:** Выделять каждой новой сети "зону влияния" (например, квадрат 100x100 тайлов). Новые модули можно ставить только внутри этой зоны. Центр зоны — точка входа (Spawn Point).
**Ответ:** Согласен с предложением

### 1.3. Визуализация и Свет
*   **Вопрос:** Мы решили, что свет не нужен. Как сделать "цифровой" вид без теней?
*   **Предложение:** В `NetrunningImmersionSystem` (клиент) при входе в сеть отключать для игрока стандартный Lighting (через `LightManager.Enabled = false` или спец. оверлей). Все объекты на карте сети должны иметь `shader: unshaded` в прототипах, чтобы они всегда были яркими и четкими.
**Ответ:** Думаю можно такое сделать

### 1.4. Комнаты и "Сшивание"
*   **Вопрос:** Как игрок будет расставлять новые комнаты?
*   **Предложение:** Сделать в UI деки вкладку "Architect". Игрок выбирает комнату, видит ее "фантом" на гриде и подтверждает установку. Система проверяет: а) доступный ресурс сервера, б) отсутствие препятствий (тайлов) в месте установки.
*   **Ответ:** Пока что можно сделать именно так

### 1.5. Персистентность (Сохранение)
*   **Вопрос:** Должен ли грид исчезать, когда игрока нет в сети? 
*   **Предложение:** Если это локальная сеть здания — она должна существовать вечно (пока цел физический сервер). Если это временная подсеть деки — она удаляется при Jack Out.
**Ответ:** Это локальная сеть здания

## 2. Комнаты локальной сети
1. Сервер создает стартовую комнату локальной сети.
2. Дополнительные комнаты не имеют встроенной специализации: каждая увеличивает лабиринт и постоянную нагрузку на физический сервер.
3. ICE, Black ICE, демоны и другие программы размещаются отдельно и работают по логике META. Комната не выдает им дополнительные слоты или способности.
4. Физические устройства представлены отдельными узлами сети и не требуют специальной комнаты-посредника.

## 3. Материализация META-программ
1. DataShard не делится на отдельные типы ICE, Black ICE или Demon. Это обычная META-программа, назначение которой определяется написанным кодом.
2. Администратор должен лично погрузиться в локальную сеть и запустить программу через UI связанной кибердеки.
3. Вызовы `SYS.SPAWN_ICE`, `SYS.SPAWN_BLACK_ICE` и `SYS.SPAWN_DEMON` материализуют программу в текущей комнате аватара.
4. Материализованная сущность получает приватную копию байткода текущего DataShard и резервирует ресурсы физического сервера.
5. Событийная защита определяется наличием `ON_EVENT("INTRUSION")`, а не отдельным типом DataShard.
6. Директива `REQUIRE TARGET [0];` разрешает запуск программы без выбранного сетевого узла, но только через HotSim-аватар. По умолчанию программа использует безопасный режим `REQUIRE TARGET [1];`.
7. `SYS.IS_NETWORK_ADMIN(PTR)` возвращает `1`, если указанная дека имеет административные права в локальной сети текущего исполнителя. Решение об атаке администратора остается частью META-кода.
8. `SYS.SPAWN_WALL(PTR server, INT x, INT y)` материализует на соседнем тайле стену, которая по умолчанию непроходима для всех. Создавшая её программа явно настраивает исключения через `SYS.WALL_ALLOW_OWNER(PTR wall, INT enabled)` и `SYS.WALL_ALLOW_ADMINS(PTR wall, INT enabled)`.
9. `SYS.SPAWN_TRAP(PTR server, INT x, INT y)` материализует многоразовый событийный хост. При входе чужого аватара он вызывает `ON_EVENT("INTRUSION")`, а после выхода разрешает повторное срабатывание.
10. `SYS.STUN_AVATAR(PTR target, INT milliseconds)` блокирует только цифровой аватар. Физический урон телу остается отдельным эффектом META-кода через `SYS.BURN_NEUROPORT`.
