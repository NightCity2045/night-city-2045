# META: модель RAM и жизненного цикла программ

Статус: принято для текущей реализации.

## RAM

- Операторы `ALLOC RAM` и `FREE RAM` удалены из языка.
- Компилятор автоматически вычисляет `RequiredRam` по уникальным переменным и максимальному временному буферу системных вызовов.
- При запуске дека резервирует `RequiredRam` физического DataShard.
- Программа с `YIELD` удерживает RAM до завершения или принудительного обрыва.
- После завершения или обрыва RAM перестаёт быть занятой процессом, но восстанавливается декой постепенно.
- Несколько одновременно работающих программ конкурируют за конечный объём RAM деки.
- Недоступная RAM восстанавливается со скоростью `recoverySpeed`, заданной в YAML для тира деки.

## Состояния DataShard

Каждый физический DataShard находится в одном из состояний:

- `READY`: программу можно запустить, изменить или извлечь.
- `RUNNING`: программа выполняется или приостановлена через `YIELD`; её RAM зарезервирована.

Во время `RUNNING` DataShard нельзя изменить или извлечь из деки. После завершения он немедленно возвращается в `READY`, однако для нового запуска деке всё ещё нужна восстановленная RAM.

## Восстановление RAM

Состояние памяти деки разделено на три части:

```text
MaxRam = CurrentRam + ReservedRam + RecoveringRam
```

`CurrentRam` доступна для запуска. `ReservedRam` удерживается активными и приостановленными программами. `RecoveringRam` уже освобождена завершившимися программами, но ещё не восстановлена аппаратурой.

Текущая скорость восстановления:

| Дека | RAM/с |
| --- | ---: |
| Самодельная | 1 |
| Корпоративная | 3 |
| Военная | 10 |

## Defensive daemon на физическом сервере

- Установленный defensive DataShard постоянно резервирует свой `RequiredRam` из `MaxLoad` сервера.
- Обработчик `ON_EVENT("INTRUSION")` получает отдельный серверный `metaGasLimit`.
- Во время исполнения он занимает один из `maxConcurrentMetaPrograms` runtime-слотов сервера.
- После исполнения DataShard немедленно возвращается в `READY`.
- Новые события во время `RUNNING` не запускают вторую копию программы.
- Занятый DataShard нельзя извлечь из сервера.
- Исключение внутри VM безопасно освобождает runtime-слот и возвращает программу в `READY`.

Параметры производительности defensive daemon принадлежат физическому серверу и не зависят от деки атакующего.
